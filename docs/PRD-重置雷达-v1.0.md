## 0. 一页结论

### 0.1 产品是什么

Reset Radar 是一个面向高频 AI 用户的实时情报网站。它持续监测 Codex Reset 相关公开信号，经规则与人工核验后，将分散在官方页面、团队成员社交账号和社区中的信息，转化为：

- 一眼能看懂的当前状态；
- 带原始证据的事件记录；
- 清楚区分事实与预测的历史数据；
- 可在 Reset 发生时主动送达的提醒。

产品首发只解决一个高频问题：

> Codex 刚刚有没有发生额外 Reset；如果发生了，影响谁、证据是什么、我需要做什么？

### 0.2 为什么值得做

高频 Codex 用户对额度高度敏感，但目前的信息体验存在四个缺口：

1. 信息分散：用户需要反复查看社交媒体、群聊、Codex 页面和社区讨论。
2. 概念混乱：个人额度自然恢复、Reset 卡、全局用量重置常被统称为 Reset。
3. 缺少证据：转发卡片经常只有结论，没有来源、适用范围和生效状态。
4. 提醒不及时：真正有价值的不是“事后知道”，而是在可用额度恢复时立刻收到消息。

### 0.3 产品不是什么

首发版本不是：

- 用户个人 Codex 额度监控器；
- 自动兑换 Reset 卡的工具；
- 没有证据的 Reset 预测器；
- AI 模型新闻聚合站；
- 同时覆盖十几个模型厂商的大而全网站。

纯网站无法在不引入高风险账号授权或本地客户端的前提下，可靠读取用户个人 Codex 账户的 5 小时/周额度。因此，个人额度剩余量和精确恢复时间不进入 v1。

### 0.4 世界级标准

本产品的“世界级”不以功能数量衡量，而以五项能力衡量：

| 能力 | 用户感知 | v1 目标 |
| --- | --- | --- |
| 准确 | 每个结论都有来源，事实与猜测不混淆 | 已确认事件零误报 |
| 及时 | Reset 发生后无需自己刷群 | 核验发布后 60 秒内完成提醒投递（P95） |
| 清楚 | 10 秒内知道发生了什么 | 首页首屏直接回答状态、范围、时间、证据 |
| 可信 | 能回看、能纠错、能解释 | 每次修改留存版本与更正说明 |
| 可传播 | 信息天然可以转发 | 每个事件生成带域名与证据等级的分享卡 |

### 0.5 首发策略

先人工跑通，再自动化：

1. 程序发现公开信号；
2. 人工判断是不是 Reset；
3. 人工确认类型、范围和证据；
4. 发布结构化事件；
5. 系统自动发送去重提醒；
6. 累积足够样本后，再评估自动确认和概率预测。

## 1. 背景与机会

### 1.1 用户现状

高频 AI 编程用户已经形成围绕额度的固定行为：

- 额度耗尽后查看 Codex 使用页面；
- 在微信群、Telegram、Discord、X 等渠道询问是否 Reset；
- 转发“预计重置时间”“24 小时概率”等卡片；
- 关注可能发布 Reset 消息的团队成员；
- 担心错过短期活动、补偿 Reset 或即将过期的 Reset 卡；
- 为恢复工作流，愿意使用更及时的通知方式。

用户提供的以下市场信号具有启发意义，但在进入对外宣传、融资材料或商业预测前必须补充可复核来源：

| 信号 | 当前文档处理 |
| --- | --- |
| 微信近三个月约 5970 条相关讨论 | 用户观察，待验证样本口径 |
| Codex + Cowork 约 2500 万活跃用户 | 待官方或可信来源核验 |
| 国外提醒产品达到百万级月活 | 待第三方流量工具和产品方数据交叉验证 |
| 高价订阅用户愿意为即时提醒付费 | 商业假设，需要付费意愿实验 |

### 1.2 现有替代方案

用户目前通过以下方式解决问题：

| 替代方案 | 优点 | 缺点 |
| --- | --- | --- |
| Codex 官方使用页面 | 个人数据准确 | 需要主动查看；主要回答个人窗口，不回答公共事件脉络 |
| 社交账号与群聊 | 速度快、有讨论 | 噪音大、易失真、无法系统检索 |
| Reset 倒计时网站 | 访问简单 | 容易混淆预测、个人恢复与全局 Reset |
| 浏览器扩展/桌面工具 | 可监控本地账户 | 安装门槛高，安全信任成本高，不符合本项目“网站”边界 |
| 手动邮件/群通知 | 实施快 | 延迟、漏发、无法规模化和去重 |

### 1.3 产品机会

短期机会是 Reset 提醒；长期机会是成为“AI 额度与可用性事件”的可信数据层：

- 面向用户：状态页、提醒、历史、规则说明；
- 面向社区：可引用的数据、卡片、徽章和小组件；
- 面向开发者：结构化 API、Webhook；
- 面向团队：多渠道广播、值班与额度恢复协同；
- 面向搜索：持续更新的规则、报错、时间与历史页面。

长期想象不等于首发范围。v1 只验证“可信事件 + 即时提醒”是否形成使用与传播闭环。

## 2. 产品目标与非目标

### 2.1 产品目标

#### 用户目标

1. 用户进入首页后 10 秒内知道 Codex 最近是否发生额外 Reset。
2. 用户能区分个人额度恢复、Reset 卡和全局用量 Reset。
3. 用户能打开原始来源，独立判断信息是否可信。
4. 用户可以订阅，并在符合条件的事件确认后及时收到提醒。
5. 用户能按自己的时区理解所有事件时间。

#### 业务目标

1. 建立“查 Reset 先来这里”的品牌心智。
2. 用可索引历史页、规则页和事件页获取长期搜索流量。
3. 用提醒订阅将一次性搜索流量转化为可触达用户。
4. 验证用户是否愿意为更快、更多渠道和团队能力付费。
5. 建立可扩展到 Claude、Grok 等平台的事件数据模型。

### 2.2 建议的 90 天成功标准

以下为产品建议目标，不代表已完成商业承诺。上线前应结合团队资源再次确认。

| 维度 | 指标 | 建议目标 |
| --- | --- | --- |
| 准确性 | 已确认事件误报数 | 0 |
| 完整性 | 高可信来源事件漏收率 | 小于 5% |
| 发现速度 | 来源发布 → 进入待审核队列 | 中位数小于 5 分钟 |
| 核验速度 | 进入队列 → 正式发布 | 中位数小于 10 分钟 |
| 投递速度 | 正式发布 → 通知服务受理 | P95 小于 60 秒 |
| 稳定性 | 网站月可用性 | 不低于 99.9% |
| 首屏性能 | 移动端 LCP | P75 小于 2.5 秒 |
| 转化 | 有效访客 → 完成提醒订阅 | 不低于 8% |
| 留存 | 订阅 30 天后仍保持开启 | 不低于 60% |
| 传播 | 已确认事件页分享率 | 不低于 5% |

### 2.3 北极星指标

**30 天有效提醒订阅者数**：过去 30 天内至少成功验证一个提醒渠道，且未退订的独立用户数。

选择原因：网站访问量容易被一次性热点放大；有效提醒订阅者同时代表信任、持续需求和未来可触达价值。

### 2.4 非目标

v1 明确不追求：

- 覆盖所有 AI 产品；
- 准确预测下一次 Reset 的具体分钟；
- 获取或托管用户 Codex 凭证；
- 读取个人额度、项目消耗或聊天内容；
- 自动购买额度、切换账号或兑换 Reset 卡；
- 用大量低质量程序化页面快速堆 SEO；
- 将社区热度包装成官方结论；
- 建立完整论坛或社交社区。

## 3. 目标用户与使用场景

### 3.1 核心用户

#### P0：高频 Codex 个人用户

- 每月支付较高订阅费用；
- 每周多次接近或达到额度上限；
- Reset 后可以立刻恢复工作；
- 已在群聊或社交平台主动寻找 Reset 信息；
- 对及时提醒的价值感知最强。

核心任务：

> 当我因为额度不足停下工作时，我想第一时间知道额外 Reset 是否已经发生，以便马上回来继续工作，而不是持续刷群和刷新页面。

#### P1：AI 社群管理者与内容创作者

- 管理 Codex、Claude、AI 编程相关社群；
- 经常转发 Reset 消息、规则解释和活动信息；
- 需要快速生成可信、可转发的信息卡。

核心任务：

> 当 Reset 相关消息出现时，我想拿到一张有时间、适用范围和原始来源的卡片，以便安全地转发给群成员。

#### P1：小型 AI 开发团队负责人

- 团队多人依赖订阅额度工作；
- Reset 会影响排期和任务分配；
- 希望将通知推送到团队已有频道。

核心任务：

> 当公共 Reset 影响团队可用额度时，我想让整个团队在同一频道得到一致消息，减少重复询问和误解。

#### P2：搜索型普通用户

- 从搜索引擎、小红书、微信搜一搜或 B 站进入；
- 只想知道报错是什么意思、几点恢复、规则怎么算；
- 使用频率低，但规模大。

### 3.2 关键使用场景

| 场景 | 用户触发 | 产品回应 |
| --- | --- | --- |
| 查“今天 Reset 了吗” | 在搜索或群聊看到传闻 | 首页展示最新状态、更新时间和证据 |
| 收到 Reset 提醒 | 已完成订阅 | 明确说明类型、范围、时间与行动建议 |
| 判断消息真假 | 收到截图或口头转述 | 事件页展示来源链和可信等级 |
| 查看历史规律 | 想判断最近 Reset 频率 | 历史时间线和间隔统计，明确非官方预测 |
| 向群内转发 | 需要快速同步 | 一键生成分享链接和社交卡片 |
| 理解 Reset 概念 | 不知道为什么别人恢复、自己没恢复 | 规则页解释三种 Reset 的区别 |
| 查看系统是否新鲜 | 怀疑网站没有更新 | 数据健康页展示最后抓取时间和异常状态 |

## 4. 产品原则

1. **事实优先于速度**：宁可晚几分钟确认，也不把传闻标成事实。
2. **预测必须低于事实层级**：预测永远不能使用与“已确认”相同的颜色、位置和通知文案。
3. **原始证据优先**：每个已发布事件至少包含一个可访问的原始来源。
4. **范围必须明确**：必须说明影响全部用户、某种方案、受影响用户，还是未知。
5. **时间必须可解释**：同时保留 UTC 原始时间与用户本地时间。
6. **核心信息无需登录**：查看状态、历史和证据不需要账户。
7. **订阅尽量轻**：首发使用邮箱验证链接管理订阅，不强迫设置密码。
8. **更正不可静默**：已通知事件发生变化时，必须记录更正并评估是否补发通知。
9. **付费购买的是送达能力，不是真相**：核心事实公开，付费层提供更快、更丰富、更可靠的触达。
10. **先人工验证，再自动化**：没有经过真实事件验证的规则，不进入自动发布。

## 5. Reset 概念与事实标准

### 5.1 三类 Reset

#### A. Personal Window Refill：个人额度窗口恢复

用户自身的 5 小时、周或其他滚动窗口在账户指定时间自然恢复。

- 每个用户时间可能不同；
- 不属于公共事件；
- 本网站 v1 不监测个人账户；
- 页面需提示用户到 Codex 官方使用页面查看个人精确时间。

#### B. Reset Credit：Reset 卡 / 可兑换重置机会

服务方将一次可用重置机会发放到用户账户，由用户主动兑换后生效。

- 发卡不等于额度已经清空；
- 可能只发给部分用户；
- 可能存在过期时间；
- v1 记录公开宣布的发卡事件，但不读取个人卡数量，也不代替用户兑换。

#### C. Usage Reset Event：公共用量重置事件

服务方主动清除某一群体的当前用量，可能面向全部用户、某个方案或特定受影响用户。

- 是 v1 的核心监测对象；
- 必须记录适用范围；
- “宣布将重置”和“确认已生效”是两个不同时间点。

### 5.2 相关但不属于 Reset 的事件

- 使用额度永久或临时上调；
- 模型发布但未重置额度；
- 服务故障恢复；
- 用户自己的订阅升级；
- 购买附加额度；
- 客户端展示延迟；
- 单个用户账户异常。

这些事件可以作为 Reset 的背景或原因，但不得计入 Reset 次数。

### 5.3 来源可信等级

| 等级 | 来源类型 | 示例 | 能否单独支持“已确认” |
| --- | --- | --- | --- |
| A | 服务方官方文档、产品内公告、官方账号 | 官方帮助页、官方状态页、产品横幅 | 可以，仍需核对适用范围 |
| B | 可确认身份的服务方团队成员公开账号 | 团队负责人、开发者公开帖 | 可以标“团队成员宣布”，不可偷换成“官方公告” |
| C | 多个互相独立的用户证据 | 多地区、多方案截图或账户变化 | 只能支持“社区已验证生效” |
| D | 单个社区用户、群聊转述、无来源截图 | 单条帖子、二手消息 | 只能进入待核验，不对外标成事实 |

### 5.4 事件状态机

```text
发现信号 → 待核验 → 已预告 → 已确认生效 → 已归档
                  ↘ 无法证实
                  ↘ 已撤回
已发布事件 → 已更正
```

| 状态 | 对外展示 | 是否发送提醒 | 定义 |
| --- | --- | --- | --- |
| detected | 否，仅后台 | 否 | 系统发现关键词或人工录入 |
| reviewing | 否，仅后台 | 否 | 正在核对来源、类型与范围 |
| announced | 是 | 仅发给选择“预告提醒”的用户 | A/B 级来源明确表示将发生 Reset，但尚未确认生效 |
| effective | 是 | 是 | 来源明确表示已生效，或得到足够独立证据确认 |
| unverified | 可选，必须弱化 | 默认不发 | 信息值得关注但证据不足 |
| corrected | 是 | 视影响补发 | 已发布字段发生实质变化 |
| revoked | 是 | 必须补发 | 原结论被来源撤回或被证明错误 |
| archived | 是 | 否 | 事件结束，进入历史数据 |

### 5.5 “已确认生效”发布条件

满足以下任一条件：

1. A 级来源明确说明 Reset 已完成，并可确认适用范围；
2. B 级来源明确说明 Reset 已完成，且至少有一条独立用户证据；
3. 至少三条相互独立的 C 级证据，跨两个以上地区或用户方案，并由审核员确认不是个人窗口自然恢复。

v1 所有 `effective` 事件必须经过人工发布，不允许程序自动发布。

### 5.6 预测展示规则

v1 不展示“下一次准确时间”或“24 小时百分比概率”。可以展示：

- 最近 30 天发生次数；
- 最近 10 次有效事件间隔中位数；
- 距离上次事件的时长；
- 明确标注为“历史参考，不是官方计划”。

满足以下条件后，v1.1 才评估概率模型：

- 至少积累 30 个定义一致的有效事件；
- 完成回测并公开方法；
- 能展示样本量、误差和最近更新时间；
- 概率提醒由用户主动开启；
- 概率信息在视觉上明显低于已确认事件。

## 6. 产品范围与版本规划

### 6.1 v1：可信 Codex Reset 雷达

#### P0 必须上线

- Codex 当前状态首页；
- 最近一次公共 Reset 信息；
- Reset 历史时间线；
- 独立事件详情页；
- 三类 Reset 解释页；
- 来源、证据等级与适用范围；
- 自动识别用户时区，可切换时区；
- 中文、英文双语；
- 邮件提醒订阅与退订；
- 浏览器 Web Push 提醒；
- 事件分享卡；
- 数据新鲜度和系统状态；
- 内部审核后台；
- 抓取、审核、发布、通知操作日志；
- 基础 SEO、站点地图、结构化数据和分析埋点。

#### P1 上线后补充

- Telegram 机器人/频道提醒；
- Discord、Slack Webhook；
- 公开只读 JSON API；
- RSS/Atom；
- 可嵌入状态徽章与小组件；
- Reset 规则与常见报错内容页；
- 事件更正提醒；
- 管理后台双人复核模式。

### 6.2 v1.1：透明预测与增长组件

- 公开预测方法和历史回测；
- “未来 24 小时信号等级”，不承诺确定时间；
- 自定义提醒条件；
- 可分享的统计卡片；
- 团队日历订阅；
- 更多程序化时区页面，但必须有独立信息价值；
- 社区提交线索入口；
- Claude 公共 Reset 事件试点。

### 6.3 v2：商业化与多平台

- Codex、Claude、Grok 等多平台统一雷达；
- 短信、电话、企业微信等付费通道；
- 团队订阅、共享频道和通知审计；
- 高配额 API 与企业 Webhook；
- 无广告或高级数据导出；
- 付费历史分析。

### 6.4 长期候选，不承诺开发

- 浏览器扩展或本地连接器读取个人额度；
- 个人额度消耗趋势与成本分析；
- 多账号额度协同；
- 自动恢复被额度阻塞的任务；
- Reset 卡到期提醒和安全兑换。

上述功能会突破“纯网站”边界，必须在用户明确调整产品形态后另立项目。

## 8. 核心用户流程

### 8.1 查询当前状态

```text
搜索/群链接进入 → 看首屏状态 → 查看适用范围 → 打开原始证据
                                   ↘ 订阅提醒
                                   ↘ 分享事件卡
```

验收标准：

- 首屏无需滚动即可看到“是否发生”“发生时间”“影响谁”“证据状态”；
- 移动端单手可完成打开来源、订阅和分享；
- 页面显示最后检查时间；
- 数据超过新鲜度阈值时，必须展示“数据可能延迟”，不能继续显示绿色正常状态。

### 8.2 订阅提醒

```text
点击提醒我 → 输入邮箱/允许 Web Push → 选择提醒类型 → 验证 → 订阅成功
```

默认设置：

- 默认只订阅“已确认生效”；
- “已预告”与未来的“高概率信号”必须由用户主动勾选；
- 邮件必须双重确认；
- 每封邮件和推送均提供取消订阅或管理入口；
- 不强迫注册密码账户。

### 8.3 信号审核与发布

```text
抓取器发现内容
    ↓
去重并生成信号
    ↓
审核员核对原文、身份、类型、范围、时间
    ↓
创建/合并事件
    ↓
预览中英文页面与通知
    ↓
发布事件
    ↓
生成页面、分享卡、Feed 和通知任务
    ↓
监控投递与后续更正
```

### 8.4 更正与撤回

```text
发现错误 → 标记受影响字段 → 填写更正原因 → 审核 → 更新页面
                                                ↘ 必要时发送更正提醒
```

必须补发更正通知的情况：

- 适用人群从“全部用户”变成“部分用户”；
- 事件类型从“额度已重置”变成“仅发 Reset 卡”；
- 原始来源撤回；
- 生效时间或产品名称错误，可能误导用户行动；
- 原事件被证明为误报。

## 9. 页面级需求

### 9.1 首页 `/`

#### 用户要回答的问题

1. Codex 今天 Reset 了吗？
2. 最近一次发生在什么时候？
3. 影响哪些用户？
4. 这是事实还是预测？
5. 我怎么第一时间收到下一次提醒？

#### 页面模块顺序

1. **首屏状态卡**
   - 当前状态：刚刚 Reset / 今日有 Reset / 暂无已确认 Reset / 数据延迟；
   - Reset 类型；
   - 适用范围；
   - 距离发生时间；
   - 绝对时间与时区；
   - 证据等级；
   - 原始来源按钮；
   - “提醒我”主按钮。
2. **最近事件时间线**
   - 最近 3～5 条事件；
   - 预告与生效分开显示；
   - Reset 卡与用量重置使用不同图形标识。
3. **历史参考**
   - 30 天次数；
   - 最近 10 次间隔中位数；
   - 明确免责声明。
4. **三种 Reset 解释**
   - 用三个短卡片解释个人恢复、Reset 卡、公共 Reset。
5. **订阅区域**
   - 邮箱和 Web Push；
   - 说明只在选定事件发生时发送；
   - 不发送营销邮件的默认承诺。
6. **数据来源与健康状态**
   - 最后检查时间；
   - 当前监控来源数量；
   - 数据管道状态。

#### 关键交互

- 页面倒计时在前端实时更新，但绝对时间由服务端提供；
- 切换时区后全站保持选择；
- 分享按钮默认分享当前事件详情页，不分享会随时间变化的首页结论；
- 用户点击来源时新窗口打开，并记录来源点击事件；
- 无新事件时不制造紧迫感。

### 9.2 Codex 专页 `/codex`

用于未来多平台扩展。v1 可与首页内容接近，但 URL、标题和结构需稳定：

- Codex 当前 Reset 状态；
- 最近公共 Reset；
- 最近 Reset 卡发放；
- 事件时间线；
- 历史统计；
- Codex Reset 规则；
- 个人使用页面入口；
- 订阅 Codex 提醒。

### 9.3 事件列表 `/events`

筛选条件：

- 产品；
- 事件类型；
- 状态；
- 适用范围；
- 日期范围。

默认按实际生效时间倒序；没有实际生效时间时按宣布时间排序并标识。

### 9.4 事件详情 `/events/{event-slug}`

每个事件页是产品最重要的“可引用事实单元”，必须包含：

- 标准标题；
- 事件状态；
- 产品与事件类型；
- 适用范围；
- 预告时间、生效时间、记录时间；
- 用户本地时区；
- 发生原因，未知时写“未说明”；
- 原始来源列表；
- 来源类型与可信等级；
- 审核说明；
- 更正记录；
- 相邻历史事件；
- 分享图；
- 订阅入口；
- 免责声明。

事件页 URL 发布后不得因标题修改而改变；必要时使用稳定 ID + 可读 slug。

### 9.5 方法论 `/methodology`

公开说明：

- 什么算 Reset；
- 哪些不算；
- 来源如何分级；
- 事件如何从“预告”变为“生效”；
- 历史间隔如何计算；
- 预测为什么不等于承诺；
- 如何提交遗漏或要求更正；
- 网站与 OpenAI、Anthropic 等厂商无隶属关系。

### 9.6 数据健康 `/data-health`

至少展示：

- 网站和 API 状态；
- 最近一次成功抓取时间；
- 各来源连接器状态；
- 通知队列延迟；
- 当前已知故障；
- 过去 30 天可用性。

健康页不得暴露后台密钥、内部错误堆栈或可被滥用的抓取细节。

### 9.7 订阅管理 `/subscribe`

- 邮箱输入与验证；
- Web Push 授权引导；
- 事件类型选择；
- 语言与时区；
- 未来支持的通知渠道占位不提前展示；
- 退订、暂停和重新开启；
- 展示最近一次发送记录，方便用户判断是否正常。

## 10. 功能需求与验收标准

### FR-01 当前状态

**需求**：系统根据最新公开事件计算 Codex 当前状态。

**验收标准**：

- 首页状态只能来自已发布事件，不直接来自未经审核的抓取信号；
- 能区分 announced、effective、corrected、revoked；
- 显示数据更新时间；
- 数据管道超过 15 分钟未成功检查时进入 stale 状态；
- stale 状态不可显示“暂无 Reset”这种确定性结论。

### FR-02 事件历史

**需求**：用户可浏览和筛选全部公开事件。

**验收标准**：

- 每条事件都有稳定唯一 ID；
- 类型、状态、范围、时间、来源至少五项完整；
- 列表与详情时间一致；
- 更正后保留公开更正说明；
- 筛选条件可通过 URL 分享和返回。

### FR-03 来源证据

**需求**：每个公开事实都可追溯到原始证据。

**验收标准**：

- 已确认事件至少有一个来源；
- 保存来源 URL、作者、发布时间、抓取时间与摘要；
- 原始页面失效后标记“来源已失效”，不得悄悄删除；
- 不全文转载受版权保护内容，只保留必要短摘录和链接；
- 截图只能作为补充证据，不能代替可用原始链接。

### FR-04 时区

**需求**：按用户本地时区显示事件时间。

**验收标准**：

- 数据库存储 UTC；
- 首次使用浏览器时区；
- 用户可手动切换并持久保存；
- 页面同时展示时区缩写或 UTC 偏移；
- 夏令时切换使用标准时区数据库处理，不能固定加减小时。

### FR-05 邮件提醒

**需求**：用户可订阅指定事件的邮件提醒。

**验收标准**：

- 双重确认后才激活；
- 同一事件、同一渠道只发送一次；
- 通知包含类型、范围、时间、证据和详情链接；
- 退订即时生效；
- 永久退信自动停发；
- 发布后 60 秒内将 95% 的提醒任务提交给邮件服务；
- 邮件发送失败有重试、告警和最终失败记录。

### FR-06 Web Push

**需求**：支持用户在浏览器接收 Reset 推送。

**验收标准**：

- 只有用户点击明确按钮后才请求浏览器权限；
- 被拒绝后不重复骚扰；
- 失效订阅自动清理；
- 点击通知进入对应事件页；
- 与邮件使用同一事件去重键。

### FR-07 分享卡

**需求**：每个事件生成适合社交平台传播的图片和链接预览。

**验收标准**：

- 包含产品、类型、状态、时间、适用范围、域名；
- 明确显示“已确认”或“历史参考”；
- 不在卡片上写无法证实的“官方”；
- 中英文分别生成；
- 事件更正后卡片版本同步更新，但历史通知保留审计记录。

### FR-08 审核后台

**需求**：运营人员能够完成信号核验、事件发布和更正。

**验收标准**：

- 支持信号合并，防止同一条消息生成多个事件；
- 发布前必须完成类型、范围、状态、来源和时间校验；
- 能预览网站、邮件和分享卡；
- 所有发布、更正、撤回记录操作者与时间；
- 高风险动作需要二次确认；
- 撤回不会物理删除历史记录。

### FR-09 数据新鲜度

**需求**：用户可以判断网站是否仍在正常监测。

**验收标准**：

- 每个连接器记录最后成功检查时间；
- 连续失败触发内部告警；
- 对外健康状态区分正常、延迟、部分故障、严重故障；
- 首页状态与健康状态联动；
- 不得在数据中断时继续显示“实时”。

### FR-10 多语言

**需求**：支持中文和英文完整体验。

**验收标准**：

- 导航、页面、邮件、推送和分享卡均双语；
- 事件事实字段共用，编辑摘要可分别维护；
- 缺少翻译时显示明确的默认语言，不得展示空白；
- 页面设置正确的语言声明和 `hreflang`。

## 12. 数据采集与运营机制

### 12.1 v1 数据源

优先级从高到低：

1. 官方文档、官方产品公告、官方状态页；
2. 已确认身份的团队成员公开账号；
3. 高质量社区频道和结构化用户提交；
4. 搜索引擎发现的相关公开内容。

群聊内容只作为发现线索。未经发布者授权，不公开群成员身份、聊天截图或第三方隐私。

### 12.2 抓取策略

- 每个来源使用独立连接器；
- 优先使用官方 API、Feed 或合法公开接口；
- 遵守平台服务条款、抓取频率和版权要求；
- 连接器失败不影响其他来源；
- 记录抓取延迟、错误类型和连续失败次数；
- 原始凭证存储在服务端密钥系统，不进入日志和前端；
- v1 不因单个关键词命中而自动发布。

### 12.3 审核运营值班

若产品承诺全球即时提醒，就必须明确运营责任，而不是只开发页面。

首发建议：

- 设定核心监测时段；
- 非值班时段在网站明确展示可能延迟；
- 每条信号由一名审核员处理；
- `scope_type = all_users` 或需向全量订阅者发送的事件，建议二次确认；
- 每次 Reset 后完成一次复盘：是否漏收、为何延迟、是否误发、用户反馈如何。

只有当连续 20～30 个真实事件证明规则稳定后，才逐步提高自动化程度。

## 13. 通知产品规格

### 13.1 通知类型

| 通知 | 默认 | 触发条件 |
| --- | --- | --- |
| 已确认用量 Reset | 开启 | 事件进入 `effective` |
| Reset 卡发放 | 开启 | `reset_credit_grant` 被确认 |
| Reset 预告 | 关闭 | 事件进入 `announced` |
| 高概率信号 | v1 不提供 | v1.1 且用户主动开启 |
| 更正/撤回 | 强制关联发送 | 用户收过原事件且更正影响判断 |

### 13.2 通知文案模板

标题必须先给结论：

```text
[已确认] Codex 用量已 Reset
```

正文必须包含：

```text
适用范围：全部用户 / 特定方案 / 受影响用户 / 尚不明确
生效时间：用户本地时间
来源：官方 / 团队成员 / 社区验证
详情与原始证据：事件链接
```

禁止使用：

- “100% 马上 Reset”之类无证据承诺；
- 只写“重置了”而不说明是用量还是 Reset 卡；
- 用“官方”描述团队成员个人账号；
- 在用户未订阅营销内容时夹带推广。

### 13.3 去重与幂等

去重键建议：

```text
subscription_id + event_id + notification_type + correction_version
```

- 发布按钮重复点击不得造成重复发送；
- 通知服务超时重试必须使用同一幂等键；
- announced 升级为 effective 可以发送第二条，但文案必须说明是同一事件的新阶段；
- 更正通知使用新的 correction version。

### 13.4 退订与隐私

- 每个渠道单独管理；
- 退订无需登录；
- 邮箱原文不得进入分析日志；
- 运营后台默认展示脱敏地址；
- 删除请求需要有明确处理流程；
- 不将订阅信息出售或用于未经同意的营销。

## 14. SEO 与内容增长

### 14.1 SEO 核心原则

SEO 页面必须先回答真实问题，不能只替换工具名和时区生成薄内容。

优先顺序：

1. 高意图状态词：Did Codex reset today / Codex 今天重置了吗；
2. 概念词：Codex Reset card 是什么；
3. 时间词：Codex usage reset time；
4. 规则词：5 小时窗口、周限额如何计算；
5. 报错词：达到使用限制后的提示原文；
6. 操作词：如何查看剩余额度、如何查看 Reset 卡。

### 14.2 v1 内容页清单

- Codex 今天 Reset 了吗；
- Codex Reset 历史；
- Codex Reset 和个人额度恢复的区别；
- Codex Reset 卡是什么；
- 为什么别人 Reset 了而我没有；
- 如何查看 Codex 使用额度；
- Codex 5 小时窗口如何理解；
- Codex 周额度何时恢复；
- Reset 预告与已生效有什么区别；
- Reset Radar 数据来源和方法。

### 14.3 技术 SEO 验收

- 公开页面服务端渲染或静态生成；
- 页面具备唯一 title、description、canonical；
- 中英文 `hreflang` 正确；
- 自动生成 sitemap；
- 事件页使用合适的 Article/NewsArticle 结构化数据，FAQ 页面只在内容真实可见时使用 FAQ 标记；
- Open Graph 与 X 卡片可用；
- 404、撤回事件和重定向策略明确；
- 管理后台和订阅 token 页面禁止索引；
- 不索引无内容的筛选组合页。

### 14.4 传播闭环

```text
Reset 发生 → 发布事件 → 自动生成分享卡 → 社群转发 → 新用户进入详情页 → 订阅提醒
```

分享卡必须具有独立信息价值，即使脱离正文也不误导。

## 15. 商业化假设

### 15.1 商业原则

- 事实查询永久免费；
- 基础提醒免费，先建立信任和规模；
- 付费购买更强的送达保障、更多通道、团队协同和数据能力；
- 不通过制造焦虑或伪造概率促成付费；
- 不在没有用户访谈和预售验证前锁死价格。

### 15.2 候选套餐

#### Free

- 公共状态、历史与规则；
- 邮件提醒；
- Web Push；
- 基础分享卡；
- 有频率限制的公开 API（v1.1）。

#### Pro（价格待实验）

- 短信、电话或更多即时通道；
- 多平台提醒；
- 自定义事件和信号等级；
- 更高 API 额度；
- 通知投递记录与备用通道；
- 无推广内容。

#### Team（v2）

- Slack、Discord、企业微信等团队频道；
- 多成员共享规则；
- Webhook；
- 事件审计与投递报表；
- 服务等级承诺。

### 15.3 首轮付费验证

在开发短信和电话前，先做无代码/半人工验证：

1. 在订阅成功页展示“极速多通道提醒”候补名单；
2. 让用户选择愿意使用的通道；
3. 测试一次性、月付和年付价格敏感度；
4. 只有出现真实支付或强意向，再接入有固定成本的通道；
5. 将退款率、到达率和用户实际恢复工作的价值纳入判断。

用户提出的 9.9 美元、国内 9.9/19.9 元可作为实验价格，不在当前 PRD 中视为最终定价。

## 17. 非功能需求

### 17.1 性能

- 移动端 LCP P75 小于 2.5 秒；
- CLS 小于 0.1；
- INP P75 小于 200 毫秒；
- 首页关键状态优先加载，不等待非关键统计；
- 分享图片异步生成，不阻塞事件发布；
- 全球用户使用 CDN 缓存，事件发布后主动失效相关页面缓存。

### 17.2 可用性与降级

- 月可用性目标 99.9%；
- 抓取异常时，已发布历史仍可访问；
- 通知服务异常时保留任务并重试；
- 分析服务异常不得影响页面和订阅；
- 首页必须展示数据是否新鲜；
- 所有关键第三方服务配置超时和熔断。

### 17.3 可访问性

- 目标达到 WCAG 2.2 AA；
- 状态不能只靠颜色区分；
- 键盘可完成查询、订阅和退订；
- 分享图中的关键信息在页面正文中也存在；
- 倒计时支持屏幕阅读器，避免每秒播报造成干扰；
- 尊重减少动画设置。

### 17.4 安全

- 后台强制多因素认证；
- 最小权限角色：审核员、发布者、管理员；
- 发布、撤回、群发等动作写入不可随意修改的审计日志；
- 所有外部输入进行验证和输出转义；
- 订阅管理链接使用高熵、限用途 token；
- 敏感配置存储在密钥管理系统；
- 日志不得包含邮箱明文、访问 token、Cookie 或第三方账号凭证；
- 设置请求限速、机器人防护和订阅滥用防护；
- 依赖和后台定期进行安全更新。

### 17.5 合规与品牌

- 明确标注非 OpenAI 官方产品；
- 不暗示获得 OpenAI、Anthropic 或其他厂商背书；
- 产品名、Logo 和页面设计避免造成官方混淆；
- 仅使用必要的商标指称；
- 邮件遵守目标市场的退订与反垃圾邮件规则；
- 隐私政策说明收集内容、用途、保存期限、第三方处理方和删除方式。

## 18. 异常与边界场景

1. 团队成员宣布 Reset，但用户反馈尚未生效。
   - 状态保持 `announced`，不得直接写“已生效”。
2. Reset 只面向特定受影响用户。
   - 范围不得写“全部用户”；通知标题应说明限制。
3. 用户自己的额度刚好自然恢复。
   - 不作为公共事件证据，除非有独立公共来源。
4. 原始帖子被删除。
   - 页面标记来源失效，进入复核，不静默删除事件。
5. 同一个 Reset 被多条来源重复宣布。
   - 合并证据，不创建多条事件。
6. 预告时间和实际生效时间跨日期。
   - 分别保存和展示，统计使用实际生效时间。
7. 只发了 Reset 卡，没有清空当前额度。
   - 事件类型必须为 `reset_credit_grant`。
8. 数据连接器全部中断。
   - 首页进入“数据延迟”，停止确定性结论和概率提醒。
9. 通知服务超时，但实际可能已发送。
   - 使用幂等键重试，避免重复消息。
10. 事件发布后发现适用范围错误。
    - 创建更正版本，并向收到原通知的用户补发。
11. 用户时区发生夏令时变化。
    - 使用 IANA 时区规则重新计算，不修改 UTC 原始数据。
12. 同一邮箱多次订阅。
    - 更新原订阅偏好，不创建重复投递对象。
13. 机器人批量提交邮箱。
    - 限速、验证码/风控、双重确认，不向未确认地址发送事件通知。
14. 没有新 Reset 很长时间。
    - 正常展示“暂无已确认事件”，不为了活跃度制造信号。
15. 统计样本太少。
    - 不显示概率，只显示原始事件数量和样本不足提示。

## 21. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Reset 事件低频且不可预测 | 用户访问频率不足 | 用历史、规则、报错页承接搜索；用提醒建立被动触达 |
| 单一社交来源依赖 | 来源封禁或接口变化导致失明 | 多来源连接器、健康监控、人工补录 |
| 抢速度造成误报 | 信任快速崩溃 | v1 人工发布、证据分级、明确状态机、更正机制 |
| “预测”被理解成承诺 | 用户投诉与品牌损害 | v1 不给具体概率；未来公开方法、样本和误差 |
| 用户误以为能查个人额度 | 体验落差 | 首页和 FAQ 明确公共事件与个人窗口的区别 |
| 竞品快速复制页面 | 功能同质化 | 护城河放在数据历史、来源网络、审核速度和订阅关系 |
| 抓取违反平台条款 | 数据源中断或法律风险 | 优先官方 API/Feed，做条款审查，保存最小必要内容 |
| 邮件进入垃圾箱 | 提醒价值下降 | 域名信誉、双重确认、发送认证、投递监控、备用通道 |
| 全球 24 小时运营成本高 | 夜间事件延迟 | 公开值班范围；逐步自动化；达到需求后设置跨时区值班 |
| 过早商业化 | 用户不信任或转化低 | 核心事实免费，先验证提醒价值，再开发付费通道 |
| 商标与“官方感”混淆 | 平台投诉 | 明确非官方，避免仿官方视觉与误导性域名/文案 |

## 22. 待验证假设与开放决策

这些问题不阻塞原型设计，但在正式开发对应功能前必须确认：

1. **品牌名与域名**：Reset Radar 是否作为正式名称。
2. **首发语言优先级**：中文先行还是中英文同步首发。
3. **运营覆盖时段**：是否承诺 24×7，还是先覆盖中国时区核心时段。
4. **首批来源清单**：哪些账号属于 A/B/C/D 级，谁负责维护。
5. **首发提醒渠道**：邮件与 Web Push 是否同时上线。
6. **预告提醒**：是否在 v1 向用户开放，还是只发送已确认生效。
7. **事件分享卡视觉**：专业状态页风格还是更适合社群传播的强视觉风格。
8. **付费实验**：9.9 美元是一次性、月付还是年付测试；国内价格是否独立。
9. **后台人员**：首发由几人审核，是否需要双人复核。
10. **数据保留期**：信号原文摘要、通知记录和订阅数据分别保留多久。

建议默认值：

- 中英文同步；
- 邮件与 Web Push 同时上线；
- 默认只推送已确认生效；
- 全量事件继续人工审核；
- 不承诺 24×7，先如实显示值班与数据新鲜度；
- 付费功能先做候补名单，不进入首发开发。

## 23. 五步决策复核

### 第一步：质疑需求

用户确实需要减少刷群、判断真假和错过 Reset 的成本；这是高频、高影响问题，值得做。

### 第二步：删除

删除首发多平台、个人额度读取、自动兑换、复杂预测、电话提醒、完整社区和一次性大规模 SEO 页面。

### 第三步：简化

最小可靠方案是“Codex 公共事件状态页 + 证据链 + 邮件/Web Push + 人工审核后台”。

### 第四步：加速

只优化发现、核验、发布、通知四段关键链路；首屏和通知延迟是首要性能指标。

### 第五步：自动化

先用真实事件积累审核样本，再自动确认、概率建模和跨平台扩展。

**结论：做，但以可信情报网站切入，不做功能堆叠型倒计时站。**
