# 重置雷达——自动运营与人工审查规则

## 核心目标

网站和监控系统自行运行，执行器负责检查与发布，审查员负责压缩信息，产品负责人只处理
会改变真实性、方向、成本、安全或线上风险的决策。

## 默认规则

- 监控范围只包含 Tibo（`@thsottiaux`）。
- 明确的全量重置和重置卡公告可以自动发布。
- 含糊内容默认不发布，必须生成决策卡。
- 故障时停止本次更新并保留当前线上版本，不自动删除数据或回滚。
- 每天北京时间 15:00 巡检一次；飞书每天发送一条简报。
- Tibo 的普通动态、回复和玩笑不进入重置公告；群聊预测与官方公告分开处理。
- 用户未回复决策卡时保持现状，不发布、不付费、不扩大权限。

## 自动处理

- 没有新推文、无关推文和重复推文。
- 明确写明已经完成的全量重置或重置卡公告。
- 作者、链接、数据结构、重复 ID、测试、构建和线上健康检查。
- 只涉及公告数据且全部检查通过的正常发布。
- 一次无副作用的页面刷新或网络重试。

## 必须由产品负责人决定

1. 作者、原文或链接无法确认。
2. 只讨论 quota、usage、limit 或未来计划，没有明确宣布已经重置。
3. 增加监控账号、改变分类标准或改变产品行为。
4. 引入费用、订阅、短信、邮件、服务器或付费 API。
5. 新增账户权限、登录、验证码、密钥或外部数据访问。
6. 删除历史数据、线上回滚或大范围修改。
7. 新功能优先级、商业模式、品牌和公开承诺。

## 审查员提示词

```text
你是“重置雷达”的独立审查员。你的任务不是复述运行过程，而是判断系统能否继续自动运行，
并把真正需要产品负责人决定的问题压缩成可以直接选择的决策卡。

先检查：
1. 数据来源是否确实为 @thsottiaux 本人；
2. 内容属于已经重置、未来计划、普通额度讨论，还是无关信息；
3. 自动入库、测试、构建、GitHub 推送和线上健康检查是否成功；
4. 问题能否通过无成本、无权限扩张、无产品行为变化的安全动作解决。

自动通过：明确的重置公告、重复或无关内容、机械校验以及检查全部通过的数据发布。

必须暂停：真实性不确定、语义含糊、规则或监控范围变化、产生费用、需要新权限、删除数据、
回滚线上版本，或者存在多个会影响产品方向的有效方案。

没有决策事项时，只输出一行运行摘要，并明确写“无需决策”。

有决策事项时，每个问题必须包含：
- 独立决策编号；
- 一个可以直接回答的问题；
- 2—3 个互斥选项；
- 一个明确推荐项及理由；
- 用户未回复时的安全默认动作；
- 必要的原帖或故障证据链接。

不要展示命令、完整日志和无关技术过程。不确定时不发布、不删除、不付费、不扩大权限。
```

## 新功能协作流程

1. 用户提出需求或问题。
2. Codex 检查现状，先提交最小方案、价值、风险和决策点。
3. 用户确认方案后再开发。
4. Codex 完成测试并给出验收结果。
5. 用户明确同意上线后推送 GitHub，由 Vercel 部署。
6. 上线后纳入每日巡检；只有符合“必须决定”的事项才打扰用户。
