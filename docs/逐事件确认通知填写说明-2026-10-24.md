# 逐事件确认通知填写说明

日期：2026-10-24。状态：本地代码与隔离测试；没有发布网站、回填真实历史资格、启用发送或发送微信消息。

此契约解决“网站已经人工确认完成，但通知后台只能识别少数英文句式”的不一致。输入是经核验的官方公告和上下文，输出是该公告的一次完成阶段通知资格。它不代表某个微信用户的个人额度已经到账。

## 在哪里填写

沿用 `website/data/reset-feed.json` 的 `announcements` 单条公告。只有人工确实核验完成时，才给这一条添加可选 `notification` 对象。不要添加到 `tibo-posts.json` 顶层，也不要直接编辑生成的 `public-snapshot.json`。

| 字段 | 填写规则 |
| --- | --- |
| `stage` | 固定为 `reset_confirmed`。预告、推测、仅讨论额度均不能填写。 |
| `confirmedAt` | 官方完成确认帖所证明的真实时刻，使用精确到秒且带 `Z` 的 UTC 时间，例如时间格式 `2026-10-24T00:01:00.000Z`。这只是格式示例，不能复制成真实事件时间。 |
| `reviewedAt` | 本次人工实际核验该公告及证据的时刻，不能早于完成或该公告最近一次修订。 |
| `evidenceSourceUrls` | 一至八条不重复的 `https://x.com/thsottiaux/status/数字` 或 `https://twitter.com/thsottiaux/status/数字` 链接。必须包含该公告现有 `url` 的原值；如果完成依赖另一条确认帖和先前预告，应一并列入。 |

只允许这四个字段。审核人、聊天记录、内部判断过程、身份、凭据和其他私有字段不要放进公开契约。公告现有编号必须与现有官方原帖编号相同。时间关系必须满足：原公告发布时间 ≤ 官方完成时间 ≤ 人工核验时间 ≤ 这次快照生成时间；原公告有 `revisedAt` 时，人工核验时间还须不早于该次修订。

## 人工核验顺序

1. 核对作者确为 Tibo，读完原帖、引用关系与必要上下文，确认已发生完成，不能只看中文标题或 `kind=full`。
2. 原公告可以先作为待确认或普通记录存在；后来出现明确完成证据时，保持同一事件编号，添加这一次完成资格，保留相应官方证据链接。`confirmedAt` 填真实完成时刻，不填此前预告、今天审核或构建的时刻。
3. 保留真实适用范围。官方没有明确账号或额度窗口时，继续说明“范围见详情／以个人账户为准”，不能补写成所有账户已重置。通知只提示公告确认并跳转详情。
4. 只有明确完成才可设置这个契约。源文有疑问、未来式、与完成证据冲突或证据无法核验时，保留待审且不添加资格。
5. 原帖改动进入既有隔离流程时，旧资格会被移除；不能为了触发通知反复删加资格或改时间。已发送、未知结果或已排队的同编号任务继续去重。源撤回后保持停发，变更前队列不会自动改用旧载荷继续发送。

当前没有新增一个自动批准的人工审核命令。人工编辑继续受原有公告校验、测试、构建和发布流程约束；本说明不授权发布、改变云发送开关或发送消息。

## 如何验证

先在网站 `website` 目录运行 `node --test lib/reset-notification.test.ts lib/public-snapshot.test.ts scripts/reset-feed-core.test.mjs scripts/tibo-monitor-core.test.mjs`，再运行 `npm run validate:data`。这两项不会回填真实确认时间或发布网站。构建会重新导出 `public-snapshot.json`，属于后续获授权发布流程，不要为了通过时间限制单独改生成时间。

后台还会检查完整快照是否超七天、确认是否属于未来、完成是否超过24小时，以及真实完成是否晚于首次扫描基线和本人授权。因此今天才核验的旧完成也可能不会发送，这是防止补发历史的限制。旧无契约公告保留原严格规则；新增契约不会追认或重发旧记录。

仅当网站发布、同一腾讯云后台部署、可信定时器、发送配置与本人手机收信逐项验收后，才能称整条提醒已接通。本地测试只使用隔离数据和模拟微信发送。
