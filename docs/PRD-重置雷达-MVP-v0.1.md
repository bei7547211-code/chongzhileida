# Reset Radar（重置雷达）MVP 产品需求文档

> 版本：MVP v0.1  
> 日期：2026-09-15  
> 状态：可直接进入页面原型与开发拆分  
> 产品形态：网站  
> 首发对象：Codex 用户  
> 开发原则：只做验证核心需求所必需的功能

### MVP 默认假设

- 首轮种子用户来自中文 AI 社群；
- MVP 界面只做简体中文，原始英文来源保留链接；
- 所有时间按访问者浏览器时区显示；
- 由一名运营者人工判断和发布信号；
- 英文站、多平台和自动抓取在验证通过后再决定。

---

## 1. MVP 一句话

> 告诉 Codex 用户：现在有没有 Reset 信号、未来 24 小时值不值得等，以及 Reset 真正发生时第一时间发邮件提醒。

网站只回答三个问题：

1. **现在 Reset 了吗？**
2. **未来 24 小时的 Reset 信号强不强？**
3. **真正发生时，怎么立刻告诉我？**

任何不能直接帮助用户回答这三个问题的功能，都不进入 MVP。

---

## 2. 为什么用户会用

### 2.1 用户处境

核心用户已经接近或耗尽 Codex 额度。他正在群里、X 或其他渠道反复确认：

- Tibo 有没有发消息；
- 今天是不是要 Reset；
- 别人是否已经恢复；
- 现在要继续等，还是去做别的事；
- 如何避免错过真正的 Reset。

### 2.2 当前痛点

- 消息散落在多个地方；
- 转发经常没有原始来源；
- “Reset 卡”“全局 Reset”“个人额度自然恢复”被混在一起；
- 用户必须持续刷新；
- 预测卡片有传播性，但不知道依据是什么。

### 2.3 MVP 核心假设

> 如果一个网页能在 5 秒内给出当前结论、信号强度和原始证据，并允许用户订阅确认提醒，那么正在等待额度恢复的用户会收藏、订阅并转发它。

MVP 的目的不是证明我们能做一个完整平台，而是验证这条假设。

---

## 3. 目标用户

只服务一种人：

> 正在使用 Codex，关心额外公共 Reset，并且不想持续刷群或社交媒体的高频用户。

暂不服务：

- 只想查看自己 5 小时/周额度恢复时间的人；
- 企业管理员；
- 普通 ChatGPT 用户；
- Claude、Grok、Cursor 等其他产品用户；
- 想自动兑换 Reset 卡的人。

原因：纯网站无法安全、可靠地读取个人 Codex 账户额度；多平台会稀释第一版验证。

---

## 4. 核心用户路径

```text
群聊/搜索/X 看到 Reset 讨论
          ↓
      打开首页
          ↓
5 秒内看懂当前状态 + 24h 雷达分 + 来源
          ↓
    输入邮箱订阅
          ↓
  Reset 确认后收到邮件
          ↓
   点击事件页 / 转发给群友
```

MVP 只有这一条主路径。

---

## 5. 核心概念

### 5.1 公共 Reset

本产品监测的核心事件：Codex 团队额外清除一批用户的使用量。

可能适用于：

- 全部用户；
- 某类套餐用户；
- 某次故障的受影响用户；
- 范围暂时未知的用户。

### 5.2 Reset 卡

官方发给账户的一次可兑换重置机会。发卡不等于额度已经清空。

MVP 可以记录“公开宣布发卡”，但必须显示为不同事件类型。

### 5.3 个人额度恢复

用户自己的 5 小时或周额度按账户时间自然恢复。这不是公共 Reset。

MVP 不读取、不预测个人额度恢复时间。首页必须有一句固定说明：

> 这里追踪的是额外公共 Reset，不是你账户里的正常额度倒计时。

## 6. MVP 功能范围

### 6.1 只做 5 个功能

| 编号 | 功能 | 用户价值 | 优先级 |
| --- | --- | --- | --- |
| F1 | 当前 Reset 状态 | 立即知道是否已经发生 | P0 |
| F2 | 24 小时雷达分 | 判断现在值不值得关注或等待 | P0 |
| F3 | 最近事件与原始来源 | 判断消息真假 | P0 |
| F4 | 邮件提醒 | 不再持续刷新 | P0 |
| F5 | 极简运营后台 | 让运营者一分钟内更新状态并群发 | P0 |

### 6.2 明确不做

- 不做用户注册、密码和个人中心；
- 不做短信、电话、微信、Telegram、Discord；
- 不做 Web Push；
- 不做个人 Codex 额度读取；
- 不做自动兑换 Reset 卡；
- 不做 Claude、Grok 等多平台；
- 不做复杂机器学习预测；
- 不做社区发帖、评论和排行榜；
- 不做付费系统；
- 不做几十个 SEO 页面；
- 不做 App、浏览器扩展和小程序；
- 不做复杂权限系统；
- 不做公开 API。

- 当前状态；
- 一句大白话结论；
- 24 小时雷达分；
- 雷达分的 2～3 条原因；
- 最后检查时间；

用户不滚动页面，也必须完成核心判断和订阅。

### 7.3 页面下半部分

只保留：

1. 最近 10 次事件；
2. Reset 与 Reset 卡的两句话解释；
3. 雷达分怎么算；
4. 非官方产品声明；
5. 隐私、退订与联系方式。

不增加博客、新闻、复杂导航或功能介绍。

## 8. 当前状态设计

当前状态与雷达分是两回事：

- **当前状态**回答“已经发生了吗”；
- **雷达分**回答“未来 24 小时信号强不强”。

### 8.1 五种当前状态

| 状态 | 页面文案 | 使用条件 | 颜色倾向 |
| --- | --- | --- | --- |
| QUIET | 暂无 Reset 信号 | 没有值得关注的新信号 | 灰蓝 |
| WATCHING | 正在观察 | 有弱信号，但不构成预告 | 蓝色 |
| ANNOUNCED | 已预告 Reset | 可信来源明确说即将 Reset | 橙色 |
| LANDED | 已确认 Reset | 可信来源或充分证据确认已生效 | 绿色 |
| STALE | 数据更新延迟 | 超过约定时间未检查数据 | 灰色警告 |

### 8.2 状态规则

- `LANDED` 必须有来源链接；
- `ANNOUNCED` 必须注明“尚未确认生效”；
- `QUIET` 不等于“今天肯定不会 Reset”；
- 超过 20 分钟没有完成一次来源检查，自动进入 `STALE`；
- `LANDED` 在首页突出展示 24 小时，之后回到 `QUIET` 或 `WATCHING`；
- Reset 卡单独显示为 `RESET CARD GRANTED`，不得使用 `LANDED`。

---

## 9. 24 小时雷达分

### 9.1 产品定义

雷达分是一个 **0～100 的公开信号强度分**，表示“未来 24 小时值得关注 Reset 的程度”。

它不是经过大样本校准的统计概率。页面固定显示：

> Radar Score measures signal strength, not a guaranteed probability.

中文版：

> 雷达分表示当前信号强度，不是官方计划，也不保证一定发生。

### 9.2 MVP 计算方式

只使用四个用户能理解的因素：

| 因素 | 分值 | MVP 判断方式 |
| --- | ---: | --- |
| 历史节奏 | 0～30 | 根据距离上次 Reset 的时间与最近 10 次间隔自动计算 |
| 团队成员信号 | 0 / 20 / 40 | 无信号 / 模糊暗示 / 明确预告，运营手动选择 |
| 产品触发事件 | 0 / 15 | 新模型、严重故障或补偿事件，运营手动选择 |
| 社区落地报告 | 0 / 5 / 15 | 无 / 单条可信报告 / 多条独立报告，运营手动选择 |

总分最高 100。

历史节奏分使用下面的固定规则，开发不得自行猜测：

```text
elapsed = 距离上次有效 Usage Reset 的小时数
median  = 最近最多 10 次有效 Usage Reset 的间隔中位数
ratio   = elapsed / median

有效历史事件少于 3 次：0 分，并显示“历史样本不足”
ratio < 0.50：0 分
0.50 ≤ ratio < 0.75：10 分
0.75 ≤ ratio < 1.00：20 分
ratio ≥ 1.00：30 分
```

只用 `Usage Reset` 计算历史节奏，Reset 卡不参与。

### 9.3 分数区间

| 分数 | 标签 | 用户理解 |
| ---: | --- | --- |
| 0～29 | LOW | 暂无明显信号 |
| 30～59 | WATCH | 值得留意 |
| 60～79 | HIGH | 信号较强，建议开启提醒 |
| 80～100 | VERY HIGH | 强信号，但仍未确认发生 |

`LANDED` 是事件事实，不使用 100 分代替。

### 9.4 防止伪科学

- 首页必须展示分数来源；
- 手动因素必须在后台留下原因和来源；
- 没有来源不能增加团队信号分；
- 样本不足时不使用“72% 概率”，只写“72/100 雷达分”；
- 每次真实事件后记录发布前的雷达分，为以后回测保留数据；
- MVP 不根据模型自己生成的推断自动加分。

### 9.5 Reset 发生后的处理

- 发布 `LANDED` 时，首页状态立即覆盖雷达标签；
- 雷达分仍保存到历史记录，但首屏改为展示“已确认 Reset”；
- 24 小时后状态自动退出 `LANDED`；
- 团队成员信号、产品触发事件和社区报告分归零；
- 历史节奏根据新的 Reset 时间重新计算。

## 10. 最近事件

### 10.1 列表字段

每条只显示：

- 日期与用户本地时间；
- 事件类型：Usage Reset / Reset Card；
- 适用范围；
- 一句话原因；
- 原始来源链接。

### 10.2 事件详情

点击某条事件进入简洁详情页 `/event/{id}`，用于分享和邮件落地。

只包含：

- 发生了什么；
- 影响谁；
- 什么时候宣布；
- 什么时候确认生效；
- 原始来源；
- 是否有后续更正；
- 返回首页与订阅入口。

没有单独的复杂事件搜索、筛选和统计系统。

## 11. 邮件提醒

### 11.1 订阅流程

```text
输入邮箱 → 点击提醒我 → 收验证邮件 → 点击确认 → 完成订阅
```

不要求注册账号或设置密码。

### 11.2 默认提醒

默认只发送两种邮件：

1. 公共 Usage Reset 已确认生效；
2. 公开宣布发放 Reset 卡。

首页增加一个非默认选项：

```text
□ 雷达分达到 HIGH 时也提醒我
```

避免把预测提醒强加给用户。

高信号邮件的触发规则：

```text
雷达分从 60 分以下首次升到 60 分及以上 → 发送一次
保持在 60 分以上继续更新 → 不重复发送
降到 60 分以下并持续 6 小时 → 重新允许下一次高信号提醒
同一用户 24 小时内最多收到一次高信号邮件
```

### 11.3 Reset 邮件必须包含

- `[Confirmed] Codex usage reset` 结论标题；
- 适用范围；
- 确认时间；
- 一句话说明；
- 原始来源按钮；
- 事件详情按钮；
- 取消订阅链接。

### 11.4 核心规则

- 同一事件不能重复发送；
- 发布失败可以重试，但不能造成重复邮件；
- 退订立即生效；
- 未验证邮箱不接收 Reset 邮件；
- 如果“全部用户”后来更正为“部分用户”，必须向原收件人发送更正；
- 不夹带与 Reset 无关的营销内容。

## 12. 极简运营后台

MVP 不做自动情报平台。运营者平时本来就在群聊和社交媒体观察，后台只负责把判断快速发布出去。

### 12.1 后台只有两个页面

#### 页面 A：更新雷达

字段：

- 当前状态；
- 团队成员信号等级；
- 产品触发事件：有/无；
- 社区报告等级；
- 2～3 条公开解释；
- 来源链接；
- 最后检查时间。

点击“发布雷达”后：首页立即更新，但不发送 Reset 确认邮件。

#### 页面 B：发布事件

字段：

- 事件类型：Usage Reset / Reset Card；
- 状态：Announced / Landed；
- 适用范围；
- 一句话说明；
- 宣布时间；
- 生效时间；
- 原始来源链接；
- 是否发送邮件。

点击发布前必须显示完整预览和预计收件人数。

### 12.2 后台验收

- 运营者可以在 60 秒内完成一次雷达更新；
- 运营者可以在 90 秒内发布一次确认事件；
- `Landed` 没有来源时禁止发布；
- 相同来源 URL 发布过时给出重复警告；
- 发布按钮重复点击不会重复建事件或发邮件；
- 所有发布记录操作者、时间和修改前后内容。

MVP 只有一个管理员账号，可以使用托管后台的安全登录能力，不自建复杂角色权限。

## 15. 关键验收标准

### 15.1 用户侧

- [ ] 用户进入首页 5 秒内能回答“现在 Reset 了吗”。
- [ ] 用户不滚动页面就能看到雷达分、原因、来源和订阅框。
- [ ] 页面明确区分公共 Reset、Reset 卡和个人额度恢复。
- [ ] 用户可以打开原始来源独立判断。
- [ ] 手机宽度下无需横向滚动。
- [ ] 时间默认按用户本地时区显示，并标明时区。

### 15.2 运营侧

- [ ] 更新雷达不超过 60 秒。
- [ ] 发布确认事件不超过 90 秒。
- [ ] 没有来源不能发布 `Landed`。
- [ ] 数据超过 20 分钟未检查，首页自动显示 `STALE`。
- [ ] 修正事件不会删除历史记录。

### 15.3 邮件侧

- [ ] 邮箱必须验证后生效。
- [ ] 事件发布后 2 分钟内邮件完成服务商受理。
- [ ] 相同事件不会重复发送。
- [ ] 退订后不再发送。
- [ ] 预测提醒和确认提醒的标题、颜色与文案明显不同。

### 15.4 质量底线

- [ ] 已确认 Reset 零误报。
- [ ] 页面显示最后检查时间。
- [ ] 网站明确标注非 OpenAI 官方产品。
- [ ] 不保存 Codex 登录凭证。
- [ ] 不把雷达分称为官方概率。

## 16. MVP 验证指标

### 16.1 唯一核心指标

**合格访客的邮箱验证订阅率。**

合格访客：通过 Reset 相关搜索、社群链接或社交媒体进入，并停留超过 10 秒的独立访客。

建议通过线：

> 至少 100 名合格访客中，有 15% 完成邮箱验证订阅。

### 16.2 辅助指标

- 首页到订阅按钮点击率；
- 邮箱验证完成率；
- Reset 邮件 30 分钟内打开率；
- 事件详情页分享率；
- 用户从原始来源返回网站的比例；
- 用户对雷达分的理解错误率；
- 从发现来源到发布事件的时间。

### 16.3 验证周期

满足以下较晚发生的条件后评审：

- 网站上线满 14 天；
- 至少经历 3 次真实的 Reset、Reset 卡或强信号事件。

### 16.4 继续或停止

#### 继续投入

- 验证订阅率达到 15%；
- 用户能正确区分雷达分和已确认状态；
- 确认邮件带来明显回访；
- 有用户主动询问短信、群机器人或更多平台。

#### 调整

- 用户访问但不订阅：检查提醒价值和订阅表达；
- 用户只看来源：强化可信数据与事件页；
- 用户误解雷达分：弱化分数、强化状态和原因；
- 多数需求是个人额度：重新评估是否突破“纯网站”边界。

#### 停止或换方向

- 有足够合格流量但验证订阅率长期低于 5%；
- 用户更愿意依赖现有群聊且不认为错过有成本；
- 无法在可接受时间内稳定获得可信来源；
- 雷达分持续制造误解且没有实际决策价值。

## 17. 开发顺序

按以下顺序开发，每一步通过再进入下一步：

### M1：假数据首页

- 完成桌面和手机首屏；
- 使用 5 个历史事件作为假数据；
- 找 5 名真实 Codex 用户测试，确认 5 秒内看懂。

### M2：后台与真实数据

- 接入四张最小数据表；
- 完成更新雷达和发布事件；
- 首页展示真实数据与最后检查时间。

### M3：邮件闭环

- 邮箱验证；
- 订阅、退订；
- 确认 Reset 群发；
- 去重、失败记录和更正邮件。

### M4：上线验证

- 接入最小分析；
- 完成隐私页和非官方声明；
- 小范围发布；
- 运行至满足 MVP 验证周期。

不要并行开发 M2、M3、M4。先验证页面理解，再做数据和通知。

---

## 18. 开发完成定义

MVP 不是“页面能打开”就算完成。必须同时满足：

1. 真实用户在 5 秒内理解首页；
2. 管理员能在 90 秒内发布带来源的 Reset；
3. 已验证订阅者能收到且不会重复收到邮件；
4. 数据过期时网站不会假装仍然实时；
5. 至少通过一次完整演练：

```text
发现信号 → 更新雷达 → 发布 Reset → 用户收到邮件 → 打开事件页 → 运营修正事件
```

以上五项缺一项，都不算 MVP 完成。

## 19. 下一步唯一动作

基于本 PRD 制作 **一个首页高保真原型**，只设计四个核心模块：

1. 当前状态；
2. 24 小时雷达分；
3. 原因与来源；
4. 邮件订阅。

先用原型测试用户能否在 5 秒内说出：

> “还没 Reset，但信号较强；我可以看来源，也可以留下邮箱等确认提醒。”

如果用户说不出这句话，先改页面，不进入开发。
